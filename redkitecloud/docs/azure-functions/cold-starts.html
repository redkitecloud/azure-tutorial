Cold Starts Explained

Cold starts are the most discussed limitation of serverless functions. When your function hasn't run recently and a new request arrives, Azure must allocate a compute instance, load the runtime, and initialise your application before executing your code. This startup delay — the cold start — can add anywhere from 200ms to several seconds to your response time. Understanding and mitigating cold starts is essential for production Functions deployments.

What is a Cold Start?

On the Consumption plan, Azure Functions scale to zero — no instances run when idle. When a new request arrives after a period of inactivity, Azure must start a fresh instance. This startup time is the cold start.

Cold StartWarm Start
WhenFirst request after idle period, or scale-out to new instanceSubsequent requests to an already-running instance
Latency added200ms – 5+ secondsNear zero
FrequencyAfter ~20 minutes idle, or when scaling outAll other requests

What Happens During a Cold Start

A cold start has several phases — each adds to the total startup time:

  1. Instance allocation — Azure finds an available VM or container slot (~50–200ms)
  2. Runtime initialisation — Load the Functions host and language runtime (Node.js, Python, .NET) (~100–500ms)
  3. Application initialisation — Load your function code, import libraries, run startup code (~100ms – 3s depending on dependencies)
  4. Function execution — Your actual code runs (warm from here)
ℹ️
Application Initialisation is the Biggest Variable The runtime startup is fairly fixed. The biggest variable is your application — how many packages you import, how large your code bundle is, and whether you make connections during startup (database connections, config loading). This is where optimisation has the most impact.

Factors That Affect Cold Start Duration

Language Runtime

Python500ms–3sSlower — interpreter startup, import overhead
Java1–5sSlowest — JVM startup is heavy
PowerShell500ms–2sMedium — PS engine startup

Other Key Factors

  • Number of imports/dependencies — More packages = longer import time
  • Package size — Large deployment packages take longer to load
  • Startup connections — Opening DB connections, loading config at startup adds time
  • Hosting plan — Consumption: cold starts occur; Premium: pre-warmed instances; Dedicated: always on
  • Operating system — Linux typically has faster cold starts than Windows for Python/Node.js

Measuring Cold Starts

Application Insights tracks cold starts automatically. In the Performance blade, filter for operations with high response time on initial invocations. You can also query Log Analytics:

KQLFind cold start requests in Application Insights
requests
| where cloud_RoleName == "myfunctionapp-2026"
| extend isColdStart = tobool(customDimensions["ColdStart"])
| where isColdStart == true
| summarize
    count(),
    avg(duration),
    percentile(duration, 95)
  by bin(timestamp, 1h)
| order by timestamp desc

8 Strategies to Reduce Cold Start Impact

1. Use Premium Plan with Pre-Warmed Instances

The most reliable fix — keeps minimum instances always warm. Zero cold starts for the pre-warmed instances. Cost: ~₹5,000+/month minimum.

2. Use Dedicated (App Service) Plan

Functions are always running — no cold starts. Best if you already have an App Service Plan.

3. Minimise Package Size

Only import packages you actually need. Use dependency management tools to exclude dev dependencies. Smaller packages = faster loading.

PythonLazy imports — only load when needed
def my_function(req):
    # Import inside function — only loads on first call to this path
    # rather than on every cold start
    import heavy_library

    return heavy_library.process(req.get_body())

4. Move Expensive Startup to Module Level (Lazy Init)

Database connections opened at module level persist across warm invocations — but still happen during cold starts. Use lazy initialisation to defer them until first use.

5. Choose C# or JavaScript/TypeScript

If language choice is flexible, C# and Node.js have the fastest cold starts. Avoid Java on Consumption plan for latency-sensitive APIs.

6. Use Keep-Alive Pings (Ping Warmer)

A Timer-triggered function (or external cron job) pings your HTTP functions every 5–10 minutes to keep them warm. A hacky workaround, but free and effective for Consumption plan.

PythonKeep-alive pinger function
@app.timer_trigger(schedule="0 */5 * * * *", arg_name="timer")  # Every 5 minutes
def keep_warm(timer: func.TimerRequest) -> None:
    import urllib.request
    # Ping the HTTP function to keep it warm
    urllib.request.urlopen("https://myfunctionapp.azurewebsites.net/api/health?code=xxx")
    logging.info("Pinged health endpoint to keep warm")

7. Enable Always Ready Instances (Flex Consumption)

The newer Flex Consumption plan supports "always ready" instances — a middle ground between Consumption and Premium pricing.

8. Optimise Startup Code

Audit your startup code — avoid synchronous network calls, large file reads, or expensive computation during module initialisation. Defer everything possible to the first actual request.

When Cold Starts Don't Matter

Cold starts only matter if users or systems experience the latency. They're irrelevant for:

  • Timer triggers — running scheduled jobs where a few extra seconds don't matter
  • Queue and blob triggers — asynchronous processing where latency isn't user-facing
  • Internal background jobs with no strict SLA
  • Development and testing functions
