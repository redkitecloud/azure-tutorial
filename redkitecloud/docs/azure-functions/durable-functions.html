Durable Functions

Regular Azure Functions are stateless — each execution is independent and forgets everything when it finishes. Durable Functions extend Azure Functions to support stateful, long-running workflows. They let you write complex multi-step orchestrations in code — chaining functions together, running them in parallel, waiting for human approval, and resuming after days or weeks — all without managing state yourself.

What Makes Durable Functions Different

Regular Functions: stateless, short-lived, forget everything after execution.

Durable Functions: stateful, can run for hours/days/months, automatically checkpoint state so they survive restarts, and can coordinate multiple functions working together.

Regular FunctionsDurable Functions
StateNone — statelessAutomatic — checkpointed in storage
DurationMax 10 min (Consumption)Days, months, unlimited
CoordinationManual (queues, events)Built-in — call activities, wait, fan-out
RetriesManualBuilt-in retry policies

Function Types

Orchestrator Function

The coordinator — defines the workflow logic. Calls activity functions, waits for results, handles retries. Must be deterministic (no random, no DateTime.Now, no async I/O directly).

Activity Function

The worker — does the actual work (call an API, write to database, send an email). Called by the orchestrator. Can use any I/O, non-deterministic operations.

Entity Function

Manages a piece of durable state — like a counter, a shopping cart, or a running total. Can be read and updated from orchestrators or other functions.

Client Function

Starts, queries, terminates, or sends events to orchestration instances. Usually an HTTP-triggered function that kicks off a workflow.

PythonDurable Functions — basic chaining pattern
import azure.functions as func
import azure.durable_functions as df

app = func.FunctionApp()
bp = df.Blueprint()

# 1. Client — starts the orchestration via HTTP
@app.route(route="start-workflow")
@app.durable_client_input(client_name="client")
async def start_workflow(req: func.HttpRequest, client: df.DurableOrchestrationClient):
    instance_id = await client.start_new("order_workflow", None, req.get_json())
    return client.create_check_status_response(req, instance_id)

# 2. Orchestrator — defines the workflow
@bp.orchestration_trigger(context_name="context")
def order_workflow(context: df.DurableOrchestrationContext):
    order = context.get_input()

    # Step 1: Validate
    validated = yield context.call_activity("validate_order", order)

    # Step 2: Charge payment
    payment = yield context.call_activity("charge_payment", validated)

    # Step 3: Send confirmation
    yield context.call_activity("send_confirmation", payment)

    return {"status": "complete", "orderId": order["id"]}

# 3. Activity — does actual work
@bp.activity_trigger(input_name="order")
def validate_order(order: dict) -> dict:
    # Validate order fields, check inventory...
    order["validated"] = True
    return order

Application Patterns

Pattern 1: Function Chaining

Execute functions in sequence — output of one is input to the next. The simplest Durable pattern — used in the example above.

Pattern 2: Fan-Out / Fan-In

Execute multiple functions in parallel, then wait for all to complete and aggregate results. Perfect for processing a list of items concurrently:

PythonFan-out/fan-in — process items in parallel
@bp.orchestration_trigger(context_name="context")
def process_batch(context: df.DurableOrchestrationContext):
    items = context.get_input()  # List of items to process

    # Fan-out: start all in parallel
    tasks = [context.call_activity("process_item", item) for item in items]

    # Fan-in: wait for ALL to complete
    results = yield context.task_all(tasks)

    return {"processed": len(results), "results": results}

Pattern 3: Async HTTP API

Start a long-running operation and return a status URL immediately. Client polls for completion. Built into Durable Functions via create_check_status_response.

Pattern 4: Human Interaction

Pause the workflow and wait for a human to approve — with a timeout fallback:

PythonWait for human approval with timeout
@bp.orchestration_trigger(context_name="context")
def approval_workflow(context: df.DurableOrchestrationContext):
    request = context.get_input()

    # Notify approver
    yield context.call_activity("send_approval_email", request)

    # Wait up to 48 hours for approval event
    deadline = context.current_utc_datetime + timedelta(hours=48)
    approval_event = context.wait_for_external_event("Approval")
    timeout = context.create_timer(deadline)

    winner = yield context.task_any([approval_event, timeout])

    if winner == approval_event:
        return {"approved": True}
    else:
        # Timed out — auto-reject
        yield context.call_activity("notify_timeout", request)
        return {"approved": False, "reason": "timeout"}

Pattern 5: Aggregator (Stateful Entity)

Accumulate events over time into a stateful entity — like a running counter or a shopping cart that persists across multiple function calls.

How State is Persisted

Durable Functions use Azure Storage (Tables, Queues, Blobs) as a backing store — called the Task Hub. The orchestrator's execution history is written to storage as events. When an orchestrator resumes (e.g., after an activity completes), it replays the history to reconstruct its current state.

Orchestrator Constraints

Because orchestrators replay their history, they must be deterministic. Do NOT use in orchestrators:

  • Random number generation
  • Current date/time (datetime.now()) — use context.current_utc_datetime
  • Direct async I/O (HTTP calls, database queries) — put in activity functions
  • Global state that changes between replays
⚠️
All non-deterministic operations go in Activity Functions Orchestrators must produce the same output when replayed with the same history. API calls, DB queries, random values — all belong in Activity functions, not the Orchestrator.
