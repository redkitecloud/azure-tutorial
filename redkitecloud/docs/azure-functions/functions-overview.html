What is Azure Functions?

Azure Functions is a serverless compute service that lets you run small pieces of code — called functions — without managing any infrastructure. You write the code, Azure handles everything else: servers, scaling, OS patching, and availability. You're billed only for the time your code actually runs — down to the millisecond. It's the cloud's answer to "I just need to run this piece of code when something happens."

What is Serverless?

Serverless doesn't mean no servers — it means you don't manage servers. The cloud provider provisions, scales, and maintains all the compute infrastructure automatically. You focus purely on your code.

How Azure Functions Works

A Function is a piece of code that runs in response to an event (called a trigger). The lifecycle is:

  1. An event occurs — HTTP request arrives, a message lands in a queue, a file is uploaded
  2. Azure detects the trigger and allocates a compute instance (may already be warm)
  3. Your function code executes
  4. The result is returned or written to an output binding
  5. Billing stops — you pay only for execution time
ℹ️
Function App vs Function A Function App is the container — the Azure resource that hosts one or more functions. All functions in a Function App share the same hosting plan, runtime, and settings. Individual Functions are the actual code files inside the Function App.

Triggers and Bindings

Triggers and bindings are the magic of Azure Functions — they connect your code to Azure services without you writing plumbing code.

Triggers

Every function has exactly one trigger — the event that causes it to run:

TriggerFires When
HTTPAn HTTP request hits the function URL
TimerA cron schedule fires (e.g., every hour)
Blob StorageA file is created/updated in a container
Queue StorageA message is added to a storage queue
Service BusA message arrives on a Service Bus queue/topic
Event HubEvents arrive at an Event Hub
Cosmos DBDocuments are inserted/updated (change feed)
Event GridAn Event Grid event is published

Bindings

Bindings declaratively connect your function to other services — reading from or writing to them without connection boilerplate code:

  • Input bindings — Read data into your function (e.g., read a Cosmos DB document)
  • Output bindings — Write data from your function (e.g., write to a queue, send an email)
PythonHTTP trigger with Blob output binding
import azure.functions as func

app = func.FunctionApp()

@app.function_name("ProcessUpload")
@app.route(route="upload")                              # HTTP trigger
@app.blob_output(arg_name="outputBlob",                # Blob output binding
                 path="processed/{rand-guid}.json",
                 connection="AzureWebJobsStorage")
def main(req: func.HttpRequest, outputBlob: func.Out[str]) -> func.HttpResponse:
    data = req.get_body().decode()
    outputBlob.set(data)          # Write to Blob — no storage SDK needed
    return func.HttpResponse("Saved!", status_code=200)

Runtime Versions

The Azure Functions runtime determines which features and language versions are available. Always use the latest:

  • Functions v4 — Current, recommended. Supports all modern language versions.
  • Functions v3 — Legacy, still supported but plan to migrate.
  • Functions v1/v2 — End of life — do not use for new projects.

When to Use Functions

  • Processing files after they're uploaded to Blob Storage
  • Running scheduled jobs (nightly reports, cleanup tasks)
  • Building lightweight REST APIs or webhooks
  • Reacting to queue messages or events
  • Integrating services (glue code between systems)
  • Any task that runs infrequently and completes in under 10 minutes
⚠️
Not Great For... Long-running processes (>10 min on Consumption plan), applications needing persistent connections, or workloads with very consistent high traffic (App Service is cheaper for always-on scenarios).
