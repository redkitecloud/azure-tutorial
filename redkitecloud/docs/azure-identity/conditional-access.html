Conditional Access

Conditional Access is the smart policy engine of Microsoft Entra ID. It evaluates signals — who the user is, where they are, what device they are on, what app they are accessing — and enforces access controls in real time. It is the "if this, then that" of identity security: if a user signs in from an unknown location, then require MFA. If the device is not compliant, then block access.

How Conditional Access Works

Every sign-in is evaluated against all applicable Conditional Access policies. A policy has three parts:

PartDescriptionExample
Assignments (Who/What)Which users, apps, and conditions trigger this policyAll users accessing Azure Portal
Conditions (When)Additional signals that refine when the policy appliesWhen signing in from outside named locations
Access controls (Then)What to do — grant with requirements, or blockRequire MFA

Conditions (Signals)

ConditionExamples
User / GroupAll users, specific groups, specific roles (Global Admin)
Cloud appAzure Portal, Microsoft 365, Salesforce, any registered app
LocationNamed locations (trusted IPs), countries, any location
Device platformWindows, iOS, Android, macOS
Device stateCompliant (Intune-managed), Entra Joined, Hybrid Entra Joined
Sign-in riskLow, Medium, High (requires P2)
User riskLow, Medium, High — based on leaked credentials, anomalous behaviour (requires P2)

Grant Controls

Grant ControlEffect
Block accessDeny sign-in entirely — no exceptions
Require MFAAllow but must complete MFA
Require compliant deviceDevice must be Intune-compliant
Require Entra Joined deviceDevice must be Entra ID joined
Require approved appMust use a Microsoft-approved client app
Require password changeForce password reset before access

Grant controls can require all selected controls (AND) or any one selected control (OR).

Session Controls

Session controls limit what can be done inside an app after sign-in:

  • Sign-in frequency — How often users must re-authenticate (e.g., every 1 hour)
  • Persistent browser session — Prevent "stay signed in" on unmanaged devices
  • App-enforced restrictions — SharePoint/Exchange block download on unmanaged devices
  • Continuous Access Evaluation — Revoke tokens in near-real-time if risk is detected

Named Locations

Named Locations define trusted IP ranges (like your office) or countries. Use them to:

  • Require MFA only when outside the corporate network
  • Block sign-ins from specific countries
  • Trust office IPs and skip MFA for compliant in-office sign-ins
Example PolicyRequire MFA outside corporate network
Policy: "Require MFA outside office"
  Assignments:
    Users: All users
    Apps: All cloud apps
  Conditions:
    Locations: Exclude named location "Corporate Office IPs"
  Grant:
    Require MFA

Report-Only Mode

Before enabling a new Conditional Access policy, enable Report-only mode. The policy evaluates sign-ins but does not enforce — you can see in the sign-in logs exactly who would have been affected before actually blocking anyone. Always test in report-only first.

Break-Glass Accounts

Always exclude at least one emergency break-glass account from all Conditional Access policies. If your MFA provider goes down or a policy is misconfigured, you need a way to sign in as a Global Admin and fix it. Break-glass accounts should:

  • Have a very long, complex password stored securely offline
  • Be excluded from all CA policies
  • Have MFA set up via a physical FIDO2 key (not phone-based)
  • Have sign-in monitored and alerted

AZ-104 Exam Tip Know that Conditional Access requires Entra ID P1. Know the three parts of a policy: assignments, conditions, access controls. Know that Report-only mode tests a policy without enforcing it. Know that named locations define trusted IP ranges. Know that break-glass accounts must be excluded from all CA policies.
