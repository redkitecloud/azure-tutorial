Azure Key Vault

Azure Key Vault is a cloud service for securely storing and managing secrets, encryption keys, and certificates. It keeps sensitive values out of application code and configuration files — eliminating the risk of credentials being committed to source control or leaked in logs. Every application that deals with secrets should use Key Vault.

Object Types

TypeWhat it StoresExamples
SecretsAny sensitive string valueDatabase connection strings, API keys, passwords
KeysCryptographic keys — used to encrypt/decrypt dataStorage encryption keys, TDE keys for SQL
CertificatesX.509 SSL/TLS certificates with their private keysApp Service SSL certificates, code signing certs

Access Models

Key Vault supports two access models — you choose one per vault:

Vault Access Policy (Legacy)

Assign permissions (get, list, set, delete) per principal at the vault level. Less granular — a principal either has access to all secrets or none. Being phased out in favour of RBAC.

Azure RBAC (Recommended)

Use standard Azure RBAC roles on the Key Vault. More granular — can assign access at the vault, secret, key, or certificate level.

RoleCan Do
Key Vault AdministratorFull management — create, delete, manage access
Key Vault Secrets OfficerCreate and manage secrets
Key Vault Secrets UserRead secret values only
Key Vault ReaderView vault properties — not secret values

Soft Delete and Purge Protection

Soft delete — When enabled (now on by default), deleted secrets/keys/certificates are retained for a configurable retention period (7–90 days, default 90) rather than immediately deleted. They can be recovered during this period.

Purge protection — When enabled, soft-deleted objects cannot be permanently deleted (purged) until the retention period expires — even by administrators. This prevents accidental or malicious permanent deletion.

⚠️
Enable Purge Protection for Production Without purge protection, an admin can permanently delete a secret immediately even if soft delete is on. Enable purge protection on all production vaults to ensure recovery is always possible within the retention window.

Accessing Key Vault from Applications

The recommended pattern — application uses a Managed Identity to authenticate to Key Vault, no credentials stored anywhere:

PythonAccess Key Vault using Managed Identity
from azure.identity import DefaultAzureCredential
from azure.keyvault.secrets import SecretClient

# Uses Managed Identity automatically in Azure
credential = DefaultAzureCredential()
client = SecretClient(
    vault_url="https://mykeyvault.vault.azure.net/",
    credential=credential
)

# Get a secret
secret = client.get_secret("DatabaseConnectionString")
connection_string = secret.value

# No credentials in code — Managed Identity handles auth

App Service Key Vault References

Reference Key Vault secrets directly in App Service App Settings without any code changes:

App Setting ValueKey Vault reference syntax
# In App Service App Settings, set value to:
@Microsoft.KeyVault(SecretUri=https://mykeyvault.vault.azure.net/secrets/DatabaseConnectionString/)

# App Service resolves this at runtime — the app receives the actual secret value
# App Service Managed Identity must have Key Vault Secrets User role

Creating and Managing via CLI

Azure CLICreate vault, add secret, grant access
# Create Key Vault
az keyvault create \
  --name mykeyvault-2026 \
  --resource-group myRG \
  --location centralindia \
  --enable-rbac-authorization true \
  --enable-purge-protection true

# Add a secret
az keyvault secret set \
  --vault-name mykeyvault-2026 \
  --name DatabaseConnectionString \
  --value "Server=myserver.database.windows.net;..."

# Get a secret value
az keyvault secret show \
  --vault-name mykeyvault-2026 \
  --name DatabaseConnectionString \
  --query value

# Grant Managed Identity access (Key Vault Secrets User)
az role assignment create \
  --assignee  \
  --role "Key Vault Secrets User" \
  --scope /subscriptions//resourceGroups/myRG/providers/Microsoft.KeyVault/vaults/mykeyvault-2026
