Azure App Service Best Practices

Running App Service correctly means more than just deploying your code. Production-ready applications need proper security hardening, resilient scaling configuration, zero-downtime deployments, cost controls, and observability. This page consolidates the most important best practices across every area of App Service.

Performance

Enable Always On

Enable Always On (Basic tier+) to prevent the app from idling and avoid cold start delays on the first request after inactivity. Required for continuous WebJobs.

Use the Right Tier

Don't under-provision. Monitor CPU and memory for 2–4 weeks, then choose a tier with headroom. A consistently 90%+ CPU app will perform poorly under load spikes.

Enable ARR Affinity Only When Needed

ARR Affinity (sticky sessions) routes the same user to the same instance — useful for stateful apps but reduces load balancing effectiveness. If your app is stateless, disable it.

Use a CDN for Static Assets

Offload static files (images, CSS, JS) to Azure CDN or Front Door. App Service should serve only dynamic content — static content from CDN is faster and cheaper.

Cache Aggressively

Use Azure Cache for Redis for session state, database query results, and frequently accessed data. Reduces database load and response times dramatically.

Reliability & High Availability

Run Multiple Instances

Always run at least 2 instances in production. A single-instance app has zero tolerance for instance failures or restarts during deployment.

Use Availability Zones (Premium v3)

On Premium v3, enable zone redundancy to spread instances across Availability Zones. Protects against a single data centre failure.

Configure Health Check

Set a /health endpoint and configure App Service Health Check. Unhealthy instances are automatically removed from the load balancer and replaced.

Use Deployment Slots for Zero-Downtime Releases

Never deploy directly to production. Deploy to staging, test, warm up, then swap. Keep the previous production in staging for instant rollback.

Enable Auto-Healing

Configure auto-heal rules to automatically restart the app when it enters degraded states (high memory, slow requests, status code errors) — before users notice.

Azure CLIEnable health check and Always On
az webapp config set \
  --name mywebapp-2026 \
  --resource-group myRG \
  --always-on true \
  --generic-configurations '{"healthCheckPath":"/health"}'

Security Hardening

Enforce HTTPS Only

Always enable HTTPS Only — redirects all HTTP traffic to HTTPS. Never serve production traffic over unencrypted HTTP.

Set Minimum TLS to 1.2

Reject TLS 1.0 and 1.1 connections — both are deprecated and vulnerable.

Never Store Secrets in Code or Config Files

Use App Settings (environment variables) and reference Azure Key Vault for all secrets. Use Managed Identities to authenticate to Key Vault without storing credentials.

Use Managed Identity

Enable a system-assigned Managed Identity on your App Service app. Use it to authenticate to Azure services (Key Vault, SQL, Storage) without any connection strings or passwords.

Restrict Inbound Traffic

Use Access Restrictions to limit inbound traffic to known IPs or service tags. If using Front Door, restrict to the AzureFrontDoor.Backend service tag only.

Disable FTP and SCM Access When Not Needed

Disable FTP (use FTPS only) and restrict SCM (Kudu) access to trusted IPs. Open FTP/SCM is a common attack vector.

Azure CLISecurity hardening commands
# Enforce HTTPS
az webapp update --name mywebapp-2026 --resource-group myRG --https-only true

# Set minimum TLS version
az webapp config set --name mywebapp-2026 --resource-group myRG --min-tls-version 1.2

# Disable FTP, keep FTPS only
az webapp config set --name mywebapp-2026 --resource-group myRG --ftps-state FtpsOnly

# Enable Managed Identity
az webapp identity assign --name mywebapp-2026 --resource-group myRG

Deployment Best Practices

  • Use deployment slots — staging → test → swap to production
  • Use CI/CD — automate builds and deployments via GitHub Actions or Azure DevOps
  • Mark environment-specific settings as slot settings — prevents production DB connection strings from accidentally being swapped
  • Run smoke tests after deploying to staging — before swapping to production
  • Keep a rollback plan — the previous production code is always in the staging slot after a swap

Scaling Configuration

  • Run at least 2 instances — never single-instance in production
  • Set meaningful min/max counts — min 2 for HA, max based on load testing
  • Always pair scale-out with scale-in rules — without scale-in, instances accumulate
  • Use schedule-based scaling for predictable patterns — pre-scale before traffic arrives
  • Set cooldown periods appropriately — scale out: 1–2 min, scale in: 10–15 min
  • Build stateless apps — store sessions in Redis, files in Blob Storage, not on the VM

Cost Optimisation

  • Share plans for low-traffic apps — multiple apps on one plan, no per-app charge
  • Buy reserved instances for stable production plans — up to 55% off with 3-year commitment
  • Stop dev/test plans overnight — compute billing pauses when stopped
  • Right-size before reserving — monitor for 2–4 weeks, then commit
  • Use scale-in rules — don't let instances accumulate overnight

Networking Security

  • Use VNet Integration — connect app to private VNet for database/service access
  • Use Private Endpoints for databases — SQL, Storage, Key Vault on private IPs
  • Put App Service behind Front Door or App Gateway — for WAF protection
  • Use Access Restrictions — restrict to Front Door service tag if using CDN/WAF

Monitoring & Alerting

  • Enable Application Insights — request tracing, exceptions, dependencies
  • Set alerts on HTTP 5xx errors — any increase above baseline is a red flag
  • Set alerts on response time — P95 response time above SLA threshold
  • Set alerts on memory and CPU — above 85% sustained triggers investigation
  • Use Log Analytics workspace — centralise logs for querying and correlation
